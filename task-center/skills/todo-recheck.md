# 长任务复查（配合任务中心插件）

用任务清单工具把多步任务显式化，收尾前用它挡住"漏做一步"。

工具名：`plugin_local_task_center_todo_write` / `plugin_local_task_center_todo_read`（由 `local.task-center` 插件注册，宿主强制加 `plugin_local_task_center_` 前缀；下文简称 `todo_write` / `todo_read`）。

## 什么时候建清单

- 任务需要 5 次以上工具调用，或用户明确给了步骤列表 → 开工前先 `todo_write`。
- 单步、琐碎、纯对话的请求 → **不要**建清单，空清单只是噪音。
- 用户中途追加需求 → 把新条目并入清单再继续，不要另起一份。

## 维护规则

1. **只留一条 `in_progress`**。开始下一步时，先把上一步标 `completed`，再把这一条改成 `in_progress`，在同一次调用里提交整份清单。
2. **完成即刻标记**。做完一步就更新，不要攒到最后一次性回填——回填的清单是回忆，不是进度。
3. **不标未验证的完成**。命令没跑通、测试没过、文件没落地，就不能是 `completed`；该是 `in_progress` 就留 `in_progress`。
4. **计划变了就改清单**。用户改需求、方案推翻、发现漏项，立刻重写清单；过期的条目改成 `cancelled` 而不是删掉，保留决策痕迹。
5. **优先级只标 `high` 用于真正的卡点**，全都标 `high` 等于没标。

## 收尾复查（关键一步）

准备向用户报告"做完了"之前：

1. 调 `todo_read`。
2. 逐条核对：`pending` / `in_progress` 的还有没有？
3. 有剩余项 → 要么做完，要么在最终回复里明确写出"未完成：X，原因是 Y"，**不允许**静默略过。
4. 全部完成或已交代 → 才算收尾。

## 反模式

- 清单建了就不更新，最后停在 3/10 —— 那还不如不建。
- 把清单当日记，每条都写一大段；一条一行，动词开头。
- 为了好看把没验证的步骤标成 `completed`。
