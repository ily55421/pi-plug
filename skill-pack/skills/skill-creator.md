# 技能创建（Skill Creator）

把可复用工作流压缩成高密度技能，再用真实提示词验证它确实比不带技能更好。

## 先收集缺失信息（只问缺的）

1. **目标**：这个技能要让模型做到什么？
2. **触发**：用户说什么话时应该激活？（要 2 个以上具体说法）
3. **边界**：哪些相近请求**不应**触发？
4. **成功标准**：一次好的执行长什么样？

用户只有模糊想法时先澄清。不要在技能里发明冗长访谈流程，也不要替用户猜。

## 流程

### 1. 查重

先看当前上下文里的技能目录（`<available_skills>` 一类的清单，只有 name + description）。有相近技能就**不要新建**，告诉用户改用 skill-refiner 扩展，或直接复用。

### 2. 定位落盘目录

| 判断 | 落盘位置 |
|---|---|
| 换个用户答案就变，或跨项目都成立 | 用户级 `~/.agents/skills/<name>/SKILL.md` |
| 只对当前项目有意义 | 项目级 `<repo>/.agents/skills/<name>/SKILL.md` |

`~/.agents/skills/` 是 pi CLI 与 PI-Desktop 共用的技能目录，写在这里两个宿主都能发现。在 PI-Desktop 里，插件也可通过 `contributes.skills` 提供技能，但那是**插件作者**的路径；用户沉淀个人技能走 `~/.agents/skills/`。

### 3. 提炼工作流

优先从**刚结束的这段对话**或用户给的过程文档里压缩，不要凭空设计。目标是"另一个模型需要的最短程序"。

### 4. 按渐进披露设计

- 触发与边界信息放 frontmatter `description`，**不要**再写 `## When to use` 段落重复一遍。
- `SKILL.md` 正文只留执行规则：流程、输出契约、失败处理。
- 大块背景/规格/变体拆到 `references/`；只有**确定性本地操作**才放 `scripts/`。

### 5. 起草 SKILL.md

骨架（顺序可调，但前几节必须快速回答"补什么输入、怎么执行、失败怎么办"）：

```markdown
---
name: <kebab-case，与目录同名>
description: <一句话能力 + 具体触发场景 + 不该触发的相邻情况>
---

# <技能名>

## 输入/前提      （可选：缺了会带错误假设硬上的信息）
## 流程           （祈使句步骤，关键步骤写明"为什么"）
## 输出契约       （产出什么形式：文件/消息/结构化数据）
## 失败处理       （失败时降级、放弃还是回报用户）
## 示例           （1-2 个真实 input→output，不要更多）
```

写作约束：

- **短、祈使句**。删掉 README 式教学、功能巡礼、API 概览、多套等价示例。
- **不要用 ALWAYS/NEVER/MUST 把模型限死**，改写成"这么做，因为不这么做会怎样"。
- 正文超过约 500 行就该拆到 `references/`。
- 假设读者是另一个模型，且不知道本项目的背景。
- 含 shell 命令时**必须给 Windows（PowerShell）等价写法**，禁止 `mkdir -p`、`/tmp`、`python3` 这类 POSIX 假设。
- 目录默认只要 `SKILL.md`（必要时加 `references/`、`scripts/`）。**不要**创建 README.md、CHANGELOG.md、install.sh、.env、assets/、evals/ 这些脚手架——技能目录是给模型读的，人类文档属于 git history。

### 6. 落盘前人工 lint

逐条过一遍，不通过就改完再继续：

- [ ] frontmatter 有 `name` 和 `description`，且以 `---` 包裹
- [ ] `name` 是 kebab-case，且与目录名一致
- [ ] `description` 写清了"何时用"和"何时不用"，≤240 字符
- [ ] 正文没有与 description 重复的触发段落
- [ ] 没有 README/CHANGELOG 之类被禁文件
- [ ] 正文里提到的 `references/xxx.md` 真实存在
- [ ] 含 shell 命令的，给了 PowerShell 等价

### 7. 短 eval（关键一步，别跳过）

拿**一个真实用户提示词**，对比"带技能"与"不带技能"的行为差异。

1. 选一个真的会触发该技能的提示词。
2. 起两个 Task 子代理并行跑：一个明确要求"读 `<技能路径>` 并据此处理 `<提示词>`"，另一个"不要加载任何技能，直接处理 `<提示词>`"。把两者的过程与产出写到 scratch 目录。
3. 自己读两份产出并下结论，覆盖 5 点：
   - 带技能**是否真的更好**？给明确判断：是/否/混合。
   - 好在哪？具体到某个流程步骤或输出契约的差异。
   - 不好在哪？是否加了多余步骤、过拟合固定格式、限制了模型判断？
   - 3-5 条具体改进建议。
   - 是否有该下沉成 `scripts/` 的重复确定性动作？带技能是否白烧了 2 倍 token 却没换来质量提升？

### 8. 只在 eval 暴露真实问题时才迭代

读结论 → 改技能 → 重跑 lint 与 eval。出现下列任一情况就停：

- 用户满意；
- 技能明显优于或持平 baseline 且无重大回归；
- 连续两轮没有实质提升。

## 输出契约

交付时回报：

- 技能名与落盘绝对路径
- frontmatter `description` 原文（这是模型决定何时加载的依据）
- 一次验证结果（带技能 vs 不带技能的结论）
- 触发方式说明

## 失败处理

- lint 反复不过：把技能**写简单些**，不要靠堆内容过关。
- eval 显示不如 baseline：先查是 description 质量问题、正文臃肿、流程过严，还是**这个技能根本不该存在**。
- 用户放弃这个想法：把半成品目录删掉，不要留半成品。

## 示例

**输入**："我刚摸清了怎么查同事的飞书日历空档，把这个做成技能。"

**好路径**：先看技能清单确认没有相近技能 → 判断这是跨项目通用的，落 `~/.agents/skills/feishu-availability/SKILL.md` → 从刚才的对话提炼最短步骤 → 写 description 含"查日历空档/找会议时间"触发词与"创建日程不要触发"边界 → lint → 用一个真实提示词做对照 eval。

**坏路径**：不查重直接新建；或把创建和查询塞进同一个技能；或建完只回报"已创建"而不做任何验证。

## 反模式速查

| 反模式 | 后果 |
|---|---|
| description 只堆关键词 | 模型不知道该何时加载 |
| 正文写成 README/教程 | 常驻上下文被浪费，触发后也不执行 |
| 一个技能塞多个不相关能力 | 触发条件互相污染 |
| 默认建 `.env`/`install.sh` | 技能是协议产物，不该有副作用 |
| 只写 bash 命令 | Windows 用户直接跑不通 |
| 跳过 eval 直接交付 | 无法证明技能比不带更好 |
