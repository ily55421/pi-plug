# 技能改进（Skill Refiner）

先诊断、再验证、后改写。**绝不无凭据重写**——没有具体问题证据时，正确动作是什么都不改。

## 流程

### 1. 收集证据

找到**具体出错点**：用户反馈的原话、失败的执行记录、或你亲眼看到的错误行为。

只有"感觉可以更好"而没有具体证据 → 停下来问用户，或直接说明不需要改。无证据重写会把技能改坏。

### 2. 读现状

读 `SKILL.md` 全文与目录结构（`references/`、`scripts/` 里有什么）。注意 frontmatter 的 `name` 与 `description` 原文。

### 3. 归因（关键一步）

按问题类型决定动作：

| 现象 | 归因 | 动作 |
|---|---|---|
| 技能里的文本写错了 / 过时了 | 技能的问题 | 改 |
| 技能没说错，但 agent 没照做 | **agent 的问题** | **不改**（或改写得更醒目，但不要加规则） |
| 环境/工具/路径变了 | 环境变了 | 更新具体命令与路径 |
| 漏了某个边界情况 | 覆盖不全 | 补该情况，不要顺手重写全文 |
| 纯风格偏好 | 偏好 | 不改，或征得用户同意 |

**"agent 没照做"是最常被误判的一类**：加更多 ALWAYS/NEVER 只会让技能更臃肿而不会让它被遵守。先想清楚是描述不清、位置不显眼，还是这条规则本就不该在这里。

### 4. 对照反模式清单

- description 写成了功能介绍，而不是"何时触发 / 何时不触发"
- description 与正文的 `## When to use` 段落重复
- 正文有 README 式废话、多套等价示例、API 概览
- 缺输出契约或失败处理
- 含 shell 命令却只有 macOS/Linux 写法，没有 PowerShell 等价
- 该拆到 `references/` 的大块内容压在主文件里
- 用了 ALWAYS/NEVER/MUST 把模型限死
- 技能里塞了多个不相关能力，触发条件互相污染

### 5. 生成最小补丁

外科手术式修改，只动问题点，保留技能原有结构与其余内容。每条补丁记录：

```
Problem:  <具体问题>
Evidence: <来自第 1 步的证据>
Rationale: <为什么这样改>
```

改完后自检：

- 补丁确实针对证据本身，而不是针对一个我"顺手发现"的问题？
- 会不会破坏既有正确行为？
- 是不是在往里塞通用最佳实践（那是膨胀，不是改进）？
- 是不是在改 skill-refiner 自己？（禁止自改，容易失控）

### 6. 应用

- 用户级技能在 `~/.agents/skills/<name>/SKILL.md`，项目级在 `<repo>/.agents/skills/<name>/SKILL.md`，直接用编辑工具改。
- **frontmatter 不可破坏**：`name` 必须保持与目录名一致，`description` 必须仍是有效的触发描述。
- 补丁后总大小保持在 100KB 以内。
- 不写入密钥。

### 7. 验证

用**同一个真实提示词**在改前/改后各跑一次对照（真的跑，或至少推演清楚每一步的差异），确认改善且没有引入回归。然后重读一遍技能全文，确认补丁落地、前后连贯。

### 8. 回报

改动摘要（改了什么、为什么）+ 验证结论。用户不满意就回到第 1 步重新收集证据。

## 输出契约

- 改动前后的关键差异（不必贴全文，给要点或 diff 摘要）
- 归因结论：这是技能的问题还是 agent 的问题
- 验证结果：改前 vs 改后的行为差异

## 失败处理

- 反复改都不见效 → 问题可能不在文本，考虑技能该被拆分、合并，或直接删除。
- 用户给不出证据 → 说明"无证据不改"，请用户提供一个具体失败的例子。

## 反模式

- 无证据重写全文（把有效内容一起改坏）
- 借"改进"之名往里加规则（规则越多，遵守率越低）
- 改 description 导致触发条件变化却没验证
- 自改 skill-refiner
