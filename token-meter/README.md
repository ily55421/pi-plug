# Token 计量（local.token-meter）

PI-Desktop 插件。记录**每次模型回复**的 token 消耗与**生成速度**（`XX tokens/s`），
并把跨会话的用量聚合成**年 / 月 / 日三级累计看板**与**按模型分列**的消耗、速度统计。

提供两个界面，共用同一份数据：

| 界面 | 位置 | 用途 |
| --- | --- | --- |
| **速度浮窗** | 透明置顶小窗，可拖到任意固定位置 | 常驻瞄一眼当前速度（`240 tokens/s`） |
| **完整仪表盘** | 右侧工作面板的停靠视图 | 累计看板、模型用量、会话累计、逐条回复明细 |

## 速度浮窗（v0.2.0 新增）

一个 **232×120 的透明、置顶、无边框小窗**，三行内容：

```
≈ 240 tokens/s
输出 729 tok · 用时 3.0s
会话 184 条 · 累计 20.22M tok
```

- **拖动定位**：按住浮窗任意位置拖动，把它放到你想固定的地方（例如输入框左下角）。位置在本次运行内保持不变。
- **关闭**：在浮窗上**右键**，用宿主的「置顶 / 最小化 / 关闭」菜单。
- **重新显示**：命令面板执行 `Token 计量：显示/隐藏速度浮窗`。
- 插件加载时浮窗**默认打开**，装完即见。

### 关于「钉在输入框左下角」

这里必须说清一个宿主限制：**插件无法自行设置窗口坐标**。宿主只给 `browser.*` 和 `views.*` 暴露 `setBounds`，插件窗口（`ui.panel` / `ui.shape:"widget"`）没有对应的 host API，窗口位置完全由宿主与用户掌握。

所以浮窗的位置是**你拖一次、它就一直待在那里**，而不是插件算出来的坐标。另外，宿主也没有给聊天消息页脚（复制/点赞/点踩/分支/用时/时间那一行）提供任何插件扩展点——`contributes` 的全部可用键是：

```
commands  views  settings  skills  agentExtensions  providers
themes  settingsDestinations  windowAppearance  sessionSources
mcpServers  services  bus  globalShortcuts
```

其中没有任何一项能把内容注入聊天流。因此「在每条回复左下角显示速度」在插件层做不到；浮窗是宿主当前唯一支持固定定位的方案。

顺带一提：宿主的**上下文用量检查器浮层**里本来就有一行「生成速度」（i18n 键 `usageThroughputLabel`），那是宿主内置的，本插件与它同公式，数字不会打架。

## 完整仪表盘

**主指标** —— 最近一次回复的生成速度，大号显示。

**最近一次回复的分项** —— 输出 / 输入 / 推理 / 缓存读取 tokens、用时、本次合计。

**本会话累计** —— 总用量、回复条数（含子智能体条数）、平均速度、峰值速度、累计用时（如 `33分8秒`）、缓存命中率。

**最近回复列表** —— 最近 20 条，每条一行：时间（`9月18日 03:25` 风格）、输出 tokens、速度、用时与分项。子智能体回复用 `meta.agentName` 标注成小徽章。

### 累计看板（v0.3.0 新增，v0.4.0 起整块随周期切换）

面板顶部是一块**跨所有会话**的累计看板，回答「今年 / 这个月 / 今天一共烧了多少」：

- **周期切换**：`日 / 月 / 年` 三个按钮。切换时**整块看板一起换**——卡片标题、四个主数字
  （消耗总量、回复条数、平均速度、累计用时）、柱状图粒度、模型用量，全部按该周期重算，
  而不是只动上面一行数字。年与月由天派生，所以三级数字**永远自洽**——不会出现
  「按月加起来对不上总量」这种事。
- **周期口径是「当前周期」**：今天 / 本月 / 今年。当前周期还没有记录时显示 0 并注明
  「无记录」，而不是悄悄退回最近一个有记录的周期（那会让「今日」下面挂着昨天的数字）。
- **消耗趋势柱状图**：粒度跟着周期走——日→最近 30 天、月→最近 30 个月、年→最近 30 年，
  升序从左到右。当前周期那一根用绿色高亮。
- **点柱子切到那一段时间**：柱子可以点。点某一根之后，卡片注释、四个主数字、明细表高亮
  与模型用量**一起**换成那个桶（例如点 09-14 就看到那一天的数字）；再点同一根回到当前周期。
  明细表的行也可以点，方便在相邻周期之间来回看。换周期会清掉选中态。
- **明细表**：按所选周期列出每一天 / 每一月 / 每一年的总量、条数、平均速度、用时（默认显示最近 14 行）。
- **模型用量**：也按周期统计，占比的分母是该周期自己的总量（如「本月 deepseek 占 48.8%」）。

### 模型用量（v0.3.0 新增，v0.4.0 起随周期切换）

按模型分列：每个模型的**消耗总量与占比**、回复条数、平均速度、峰值速度、缓存命中率、覆盖天数。
按总量降序，占比条直观显示谁是大头。列表跟随所选周期（今日 / 本月 / 今年），
占比分母是该周期总量。全历史口径下的实际分布：

```
codely-core           539.5M  35.4%   3130 条   均速 485   峰速 5592   5 天
step-5-preview          2.3M   0.2%     51 条   均速  48   峰速  117   2 天
```

### 速度浮窗第三行

浮窗显示的是**本会话**累计（`会话 184 条 · 累计 20.22M tok`），
完整的三级累计看板在面板里——浮窗只有 232×120，塞不下年/月/日三个维度。

## 数据来源与口径

### 速度口径（与宿主内置读数完全一致）

宿主渲染层里本来就有一个「生成速度」显示，其计算函数是：

```js
function tokensPerSecond(outputTokens, durationMs) {
  if (!Number.isFinite(outputTokens) || outputTokens <= 0) return undefined;
  if (!Number.isFinite(durationMs) || durationMs <= 0) return undefined;
  return Math.round(outputTokens / (durationMs / 1000));
}
```

即 **速度 = round(输出 tokens ÷ (用时 ÷ 1000))**，单位 `tokens/s`。本插件使用同一公式，
因此两个界面上的数字和宿主内置读数不会打架。

需要注意：这个口径用的是**整段响应时长**，所以包含首字延迟（TTFT）。它不是「纯解码速率」，
长输入导致的慢首字会拉低读数——这与宿主行为一致，是刻意的对齐而非缺陷。

### 用时从哪来

转录本里每条助手回复都带 `meta.responseDurationMs`，这是宿主的权威值，标记为 `reported`。
当它缺失时按以下顺序退化，并在 UI 上用 `≈` 标记为估算值：

1. `Date.now() - createdAt`，仅当该记录足够新鲜（≤5 分钟）时使用——这正是宿主自己的退化口径；
   对陈旧历史记录这样算会得到几分钟甚至几小时的荒唐用时，所以加了新鲜度上限。
2. 与**下一条**助手回复的时间间隔（上限 10 分钟）。这是插件读取历史时的合理近似，
   至少量级正确，且一律标记为估算。

### 数据来自两处本地记录

| 来源 | 位置 | 用途 |
| --- | --- | --- |
| 会话转录本 JSONL | `~/.pi-desktop/sessions/<sessionId>.jsonl` | 主来源，逐条回复的 token 与用时 |
| 宿主 SQLite | `~/.pi-desktop/pi.sqlite` 的 `turns` 表 | 兜底：补齐转录本未计入的回合 |

- 只取 `type === "message" && role === "assistant"` 且带 `meta.usage` 的记录。
- 排除 `*.revisions.jsonl`（编辑历史）与 `import-codex-*` / `import-claude-code-*`（导入文件），
  否则会重复计数。
- `turns` 表用 `node:sqlite` 的 `DatabaseSync(file, { readOnly: true })` 只读打开，
  拿不到该模块时静默降级（失败是预期而非异常）。
- 数据库只在「最新一条回复的 id 变了」时才重读，避免每次轮询都开库。
- 数据库的用途是补足差额：同一会话同一天的回合合计若大于转录本合计，只补差额，不与 JSONL 重复计数。

### 活跃会话的判定

两个界面都拿不到「当前会话 id」，因此用**最近修改**的会话文件作为活跃会话的稳健近似
（按 mtime 取最新的 `*.jsonl`）。

### 刷新策略

- 实时快照：插件进程轮询 1200ms；浮窗 1000ms（隐藏时 5000ms）；面板 1500ms（隐藏时 6000ms）。
- 首扫做一次完整读取；之后**只读文件尾部 128 KiB**，按记录 id 去重后追加。
- 两个条件会退回完整扫描：活跃会话换文件了；或文件增长量超过一个尾部窗口（可能漏记录）。
- 只有数据指纹变化时才写设置——每次写都会落盘，不必要地写纯属浪费磁盘。
- **累计统计走 60 秒的独立节奏**：它要读**所有**会话文件（本次核对 56 个 / 214 MB，
  冷扫约 2.2 秒），放进 1.2 秒的轮询里会把插件进程拖住。稳态下按文件指纹命中缓存，
  只需几毫秒（实测冷扫 2234ms → 热缓存 7ms）。
  缓存落在**插件自己的数据目录**（`history-cache.json`），先写 `.tmp` 再改名，
  进程被杀不会留下半截 JSON；缓存损坏或版本不符都只是「退化成全量重扫」，不是错误。


## 升级后界面没变？这是宿主的已知行为（0.3.1 起自动恢复）

宿主在**「安装插件包」覆盖已有插件**时，只会重载插件进程，**不会**销毁已有的视图
webview。销毁视图只发生在另外四条路径上——停用、卸载、插件崩溃、开发插件重载。

后果是：覆盖安装后，插件进程和浮窗已经是新的，但**右侧工作面板里可能仍在跑安装前
那份旧页面**——数据是新的（页脚时间在跳），界面却是旧的（新卡片不出现）。

0.3.1 起插件会自检：插件进程把版本号随快照发布，两个视图比对发现落后就自行
重新加载一次（守卫存在 sessionStorage，同一版本只刷一次，避免磁盘页面较旧时刷屏）。

**当前这次升级仍然需要手动触发一次**，因为正在运行的那份旧页面里还没有这段自检代码。
二选一即可：

1. **停用再启用**这个插件（插件页里切换一次开关）——最直接；
2. 或者**重启 PI-Desktop**。

之后再升级就不必手动操作了。

## 权限与隐私

**权限：`ui.view`（面板视图）+ `ui.panel`（浮窗）。**

读宿主记录走插件**自己进程内的原生 Node fs**。宿主的权限网关只覆盖宿主 API 表面，
不介入原生 Node 调用，因此本插件**不声明** `fs.read` / `session.read`，信任等级最低。
这是刻意的取舍，配套约束是：本插件对宿主**严格只读**。

- 不联网：无 `net.fetch`，manifest 里没有 `net.domains`（空 = 完全无出网）。
- 唯一写入是**自己插件数据目录**里的聚合缓存 `history-cache.json`，宿主目录与其他位置都不写。
- 快照与累计看板里只有**截断到 8 位**的会话 id、模型 id、token 计数、时长与时间戳；
  不含消息正文、工具参数、项目路径或任何凭据列。
- 不保存完整会话 id。
- 浮窗是宿主提供的透明窗口，插件既不能设置它的坐标也不能自行移动它。

## 安装

### 方式一：从打包文件安装

插件页 →「**安装插件包**」→ 选 `dist/local.token-meter-0.4.1.zip`（或 `.piplug`，两者字节相同）。
宿主的文件选择器过滤器是 `extensions: ["piplug", "zip"]`，两种都接受。

### 方式二：作为开发插件热加载

把 `token-meter` 目录作为开发插件加载即可，保存即热加载，无需重启。
注意：**放宽 `permissions` 需要显式重新加载**——热加载绝不会自动授予用户没批过的权限。

### 重新打包

```
PluginCheck(path="token-meter")   # 校验，修掉所有 error
PluginPack(path="token-meter")    # 产出 dist/<id>-<version>.piplug
```

`.piplug` 是 **store-only（不压缩）zip**，必须用 `PluginPack` 生成，不要用 `zip` / `tar`。

## 使用

1. 装好后浮窗会自动出现在屏幕上，把它拖到你想固定的位置。
2. 在任意会话里让模型回复一次，浮窗顶部就变成 `XX tokens/s`。
3. 右侧工作面板里的 **Token 计量** 视图（`order: 45`）提供完整明细。
4. 两个界面都跟随宿主主题自动切换明暗。

## 已知边界

- **不是逐 token 实时速度**。宿主把 `responseDurationMs` 与 `usage` 一起写入转录本，
  插件只能在这个粒度上读取；显示的是「每次回复完成后」的稳定读数，不是流式过程中的瞬时值。
- **浮窗位置由用户拖动决定**，插件无法设置坐标（宿主未开放该 API）。
- **无法注入聊天消息页脚**：宿主没有提供消息级的插件扩展点。
- 历史记录缺少 `responseDurationMs` 时，速度是估算值（UI 用 `≈` 标出）。
- 子智能体（subagent）的回复会一并计入会话累计，用 `agentName` 徽章区分。
- 活跃会话用 mtime 近似判定；若你在多个窗口同时开不同会话，显示的是**最近被写入**的那个。
- **累计看板的峰值速度会排除「用时过短」的样本**：宿主偶尔上报 1ms 这类读数（92 tok / 1ms
  = 92000 tok/s），这是计时精度噪声而非真实速度。低于 100ms 的样本仍计入总量与平均，
  只是不参与峰值；被排除的条数会随数据一起发布（`implausible` 字段），不是静默丢弃。
- **累计看板的用时有三档来源**：`reported`（宿主上报）、`gap`（与下一条回复的间隔估算）、
  `unknown`（两者都没有）。三者之和恒等于回复条数，所以「累计用时」可以自己解释自己。
- 累计统计走 **60 秒**的独立节奏，不是秒级刷新——它要读全部会话文件（本次核对 56 个 /
  214 MB，冷扫约 2.2 秒），年度/月度数字本来也不需要秒级新鲜度。
- **周期看板的数字走 60 秒节奏**，所以刚跨过零点时「今日」可能还残留昨天的读数，最多 60 秒后
  自行归零（插件进程的重发布指纹里带了周期 key，跨天会触发一次重新发布，不需要你手动刷新）。
